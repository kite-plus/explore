# 推荐流

> 状态：R0 完成。v0.1.10 在线上开通了打分（DeepSeek），v0.1.11 把四档评分换成三项打分，并改成天内分高的在前，v0.1.12 按实测分布把入选门槛定为 11。下一步是 R1。规则以 [accounts.md §3.1](accounts.md#31-推荐评分) 为准 · 最近更新：2026-10-05

推荐流回答一个问题：收录的博客最近写了哪些值得读的文章。它是编辑式的精选，不是"猜你喜欢"：同一时刻所有人看到的推荐相同，排序只看文章本身。本文规划推荐流从"写好了但没开"走到"每天有内容、排得对"。

## 0. 现状

v0.1.6 实现了第一版（[accounts.md §3.1](accounts.md#31-推荐评分)）：打标签的同一次模型调用给文章评一档（`skip`、`brief`、`solid`、`standout`），推荐流收 `solid` 和 `standout`，同一博客每天最多 `policy.RecommendedPerBlogPerDay` 篇，`standout` 的排序时间再加 `policy.StandoutBoost`。

线上的推荐流一直是空的。2026-10-05 在 explore.kite.plus 只读查询的结果 `[EV]`：

| 项 | 数值 |
|---|---|
| 展示中的博客 | 1,048（中文 818，英文 230） |
| 缓存的文章 | 22,029（订阅源 16,436，站点地图 5,593） |
| 已评分、已打标签 | 0 |
| 近 30 天的新文章 | 2,108 篇，约 71 篇/天，来自 565 个博客 |
| 摘要 | 平均 96 字，467 篇订阅源文章没有摘要 |
| 自带分类 | 55% 的订阅源文章有 |
| 设了默认标签的博客 | 0 |

原因是生产没有配置 `EXPLORE_TAGGER_MODEL`，打标签循环没有启动。由此还有几个问题：

1. **标签筛选在线上也是空的。** `/api/v1/tags` 总是返回全部 15 个标签，读者选哪个都得到空列表。
2. **`standout` 的提前量和按天分组冲突。** 网页（`EntryStream.astro`，中文页按 Asia/Shanghai，英文页按 UTC）和 iOS（`DayGroup.swift`，按设备时区）都按发布日期给连续的文章分组。前天的出色文章加了两天排到最上面，带着前天的日期标题，下面才是"今天"，再往下前天的标题又出现一次。线上没有评分，所以还没有人看到。
3. **评分没用真实样本校准过。** [accounts.md §4](accounts.md#4-文章标签) 要求上线前用样本实测质量、token 和费用，这一步还没做。模型只看标题、不到 140 字的摘要、分类和语言，`solid` 和 `brief` 未必分得开；分布偏到哪边，推荐流就会变成"最新减掉几篇"或者几乎为空。
4. 系统提示约 700 到 900 token（按字符估算），低于 Claude Haiku 4.5 的最小缓存长度 4,096 token，在 Haiku 上 `cache_control` 不起作用。费用本来就小（§3），只是别以为它在省钱。

## 1. 边界

推荐流继承 [architecture.md §0.1](architecture.md#0-两个核心判断) 和 [accounts.md §0](accounts.md#0-边界)，本文不修改它们：

- **不存正文。** 同步时可以从订阅源算出数字（长度、代码块数），不保存文字。
- **只依赖订阅源、模型评分和当前时间。** 清空 `entries` 重建后推荐流不变，模型结果的细小差异是唯一例外。
- **不收集读者行为，不做热度排序。** 不记点击、阅读和停留时长，不按订阅人数给博客加权，小博客的好文章和大博客的排在一起。
- **排序键固定。** 不用随时间衰减的分数，游标翻页不重复、不漏。

能用的信号：

| 信号 | 来源 | 现状 | 用途 |
|---|---|---|---|
| 标题、摘要、自带分类、博客语言 | 订阅源 | 已入库 | 模型评分的输入 |
| 评分（四档） | 模型 | 已实现，线上未开 | 入选和排序 |
| 正文长度，代码块、图片、小标题的数量 | 同步时从订阅源全文算出，只存数字 | R1 | 模型评分的输入 |
| 原文链接是否失效 | 链接检测 | 已实现 | 剔除失效文章 |
| 发布时间 | 订阅源 | 已入库 | 分天和天内排序 |
| 读者选的标签和语言 | 读者自己的设备 | R3 | 筛选 |

不用的信号：点击和阅读记录；订阅人数；订阅源里的评论数（`slash:comments` 只有部分博客系统输出，而且是热度）；外部站点的热度，比如 Hacker News 分数；正文向量。等收录到标签已经区分不开的规模，再讨论向量。

## 2. 分期

### R0 开通与校准

目标：线上推荐流每天有内容，评分可信，日期不乱。

1. **评测命令。** 新增一个评测命令（暂名 `explore tagger eval`）：随机抽给全文的订阅源（约一半，见 R1），取近 60 天的文章共 300 篇，每个博客最多 1 篇，中英比例和收录一致，按线上同样的方式生成模型输入。全文只留在评测进程的内存里，交给更强的模型（Claude Opus 5.5）读全文给出参考评分，不入库。只给摘要的订阅源另抽 50 篇，由维护者打开原文人工评（可选）。被测的是 Claude Haiku 4.5、Claude Sonnet 5.5，以及 OpenAI 兼容接口上的候选（比如 DeepSeek），都用现有输入，各跑两遍；R1 的新输入也用它比较。输出：
   - 四档的分布；
   - 和参考评分的一致程度：进不进推荐的准确率和召回率，`standout` 的准确率；
   - 同一配置两遍之间的一致率，也就是重建一致性的例外有多大；
   - 每篇实际用的 token 和费用。

   维护者再看 50 篇分歧最大的样本，确认参考评分本身靠得住。
2. **定模型和入选线。** 选进不进推荐准确率高、两遍一致率高的配置，价格是次要的（§3）。2026-10-05 用 DeepSeek（`deepseek-flash`）试评线上 40 篇 `[EV]`：关掉思考每篇 0.7 秒，四档分布为 skip 0、brief 18、solid 22、standout 0；开着思考每篇 4.5 秒，35/40 篇进不进推荐的结论相同。所以关掉思考；又因为四档几乎不给最高档、过半落在第二档，换成三项打分（[accounts.md §3.1](accounts.md#31-推荐评分)）。数据库存分数，入选门槛 `policy.RecommendedMinScore` 按实测分布定，调门槛不用重评。

   v0.1.11 上线后（`temperature` 设为 0）实测 `[EV]`：最新的 1,516 篇里，分数 ≥ 12 的占 7%，≥ 11 占 15.5%，≥ 10 占 31%，≥ 9 占 57%，记 0 分的广告和测试文章占 5%；13 分以上不到 1%，模型很少给 5 分。按北京时间分天、每个博客每天最多 1 篇算，最近 19 天里门槛 10 每天平均 21 篇（10 到 33），11 每天平均 10 篇（4 到 16），12 每天平均 5 篇。门槛定为 11：每天十篇左右，大约六七篇里挑一篇；10 会放进三分之一的文章，推荐流又会接近最新流。
3. **排序改为天内分高的在前。** 去掉 `StandoutBoost`：推荐流按天分组，天内按分数从高到低，同分按发布时间倒序。"天"按读者看的时区算：`GET /api/v1/entries` 增加 `tz` 参数（IANA 时区名，缺省 UTC），网页中文页传 `Asia/Shanghai`，英文页传 `UTC`，iOS 传设备时区；每个博客每天的上限也按这个时区计。排序键是（日期，分数，发布时间，id），固定不变，游标照旧不透明（[data-model.md §4.3](data-model.md#43-推荐流)）。推荐页的说明文字（"出色的在顶部多留两天"）一起改。
4. **监控。** `GET /api/v1/admin/overview` 和工作台加上待评积压、近 7 天四档分布、近 24 小时推荐篇数。
5. **上线。** 在选定的模型服务商那里给 Explore 单独建 API key，设用量上限；生产 `.env` 配好接口类型、地址、密钥和模型（[project-layout.md §4](project-layout.md#4-配置)）。只评按发布时间最新的 `policy.TagWindow`（1 万）篇，按每分钟 `policy.TagsPerMinute` 篇从新到旧评，约 8 小时评完，第一个小时就能评完最近两周多的文章，标签筛选同时恢复。

实施时先改 accounts.md §3.1（规则移到本文）、api.md 和 frontend.md，再改代码。

这样设计的理由：

- **先测再开。** 推荐流好不好几乎全看评分分布。不测就开，最可能的结果是每天几十篇、和最新差不多，读者看不出推荐的意义。
- **参考评分读全文。** 线上模型只能看标题和摘要，这是原则决定的。评测时让更强的模型读全文，才量得出只看摘要丢了多少，R1 值不值得做也由它回答。全文只在评测进程的内存里，和不存正文不冲突。
- **天内排序，不再提前两天。** 两端都按天分组，提前量一定会让日期标题乱序。天内排序保留了"好文章在前"，日期也不乱；代价是前天的出色文章排在今天的扎实文章后面，R2 再看要不要补"近两天出色"。
- **时区跟着读者。** 网页和 iOS 本来就按各自的时区分天，服务端按同一个时区排序，分组才对得上。

### R1 更准的评分

目标：让模型知道文章多长、有没有代码和图，少被标题带偏。

- **测量 `[EV]`。** 2026-10-05 随机抽 80 个订阅源，77 个解析成功：每篇文字长度的中位数到 1,000 字的有 40 个（52%，基本是全文），不到 300 字的 28 个（36%，只给摘要），其余 9 个在两者之间。抽到的 385 篇里，22% 有代码块，33% 有图片，37% 有小标题。
- **同步时算，只存数字。** `entries` 增加 `text_runes`、`code_blocks`、`images`、`headings` 四个整数列，从订阅源里较完整的那份文字（`content` 或 `summary`）算出。快照里文章长度的中位数不到 300 字时，视为这个订阅源只给摘要 `[待定]`。它们和其他列一样是缓存，清空后由下一轮抓取恢复；整数列存不进文字，"存不进去"的约束不变。
- **交给模型。** 输入加一行：给全文的写"约 3,400 字，5 个代码块，2 张图，4 个小标题"；只给摘要的，以及站点地图里的文章，写"长度未知"。
- **用 R0 的评测命令验收。** 进不进推荐的准确率明显提高才上线；上线后重评近 90 天的文章 `[待定]`。
- 顺带可以在文章行显示"约 8 分钟读完"，只对给全文的订阅源显示 `[待定]`。

### R2 排序与版面

R0 上线跑两周、看过真实分布之后再定：

- **每天的篇数。** 如果每天还有几十篇，网页每天先显示前 10 篇，其余收起为"这天还有 N 篇" `[待定]`。
- **近两天出色。** 如果读者常错过前一天的出色文章，推荐页顶部加一个最多 6 篇的"近两天出色" `[待定]`。
- **推荐流的订阅源。** 增加 `/recommended.xml`，格式和 `/feed.xml` 相同，读者可以在任何 RSS 阅读器里订阅推荐流。它是开放标准，也最贴合 Explore 的定位。
- **出色标记。** 文章行给 `standout` 加一个小标记。
- 可收录的标签落地页（[accounts.md §4](accounts.md#4-文章标签) 的 `[待定]`）可以复用推荐流，等有搜索流量的数据再说。

### R3 原则内的发现与个性化

不收集行为也能做：

- **同类博客。** 博客页列 5 个同类博客，按近期文章的标签分布和语言算相似度。只依赖订阅源和模型标签，可以重建。
- **多标签筛选，偏好存在读者自己的设备上。** `tag` 参数接受多个值（任一匹配），新增 `exclude_tag`；网页把常用筛选存进 `localStorage`，iOS 存进 UserDefaults。服务端不知道谁选了什么，匿名访问仍然零 Cookie。

要修订原则才能做（§4 第 3 条）：

- 已登录的读者在推荐流里隐藏已订阅的博客，它们在订阅流里已经有了。
- 按读者订阅的博客推荐同类博客。

这两项只用读者自己交给我们的订阅列表，不新收集任何数据，但仍然属于 architecture.md §0.1 写明不做的个性化推荐。

## 3. 费用

价格按 Anthropic 2026-09-25 的价目表 `[EV]`：Claude Haiku 4.5 输入每百万 token $1、输出 $5，最小缓存长度 4,096 token；Claude Sonnet 5.5 输入 $2、输出 $10、缓存读取 $0.20，最小缓存长度 512 token（上线前再核对）；Batch API 半价。

按每篇系统提示约 700 到 900 token、文章约 200 token、输出约 30 token 估算：

| | Claude Haiku 4.5 | Claude Sonnet 5.5 |
|---|---|---|
| 每篇 | 约 $0.0012，提示太短不缓存 | 积压时约 $0.0009（命中缓存），平时约 $0.0025 |
| 积压 2.2 万篇，一次 | 约 $25 | 约 $20 |
| 每天约 71 篇，每月 | 约 $2.5 | 约 $5 |

R0 评测一次约 $10，大头是 Claude Opus 5.5 读全文给参考评分。

打分也可以走 OpenAI 兼容接口（[accounts.md §4](accounts.md#4-文章标签)），比如 DeepSeek，价格按各家的价目表，一起放进 R0 评测比较。

钱不是选型的约束，按评测出来的质量选。Sonnet 5.5 默认开着自适应思考，思考 token 按输出计费，上表没算进去；用它时设 `EXPLORE_TAGGER_EFFORT=low`，评测时一并量。积压阶段改用 Batch API 能再省一半，但要多写一套异步轮询，不值得。

## 4. 需要拍板的

1. **R0 的花费和 key。** 已定（2026-10-05）：用 DeepSeek 的 `deepseek-flash`，关掉思考、`temperature` 设为 0，只评最新的 1 万篇。按它的价目表，一次评完约 $1 到 3，之后每月约 $0.2 到 0.7。
2. **排序。** 已定：按天倒序，天内分高的在前（R0 第 3 条，v0.1.11）。
3. **个性化的边界。** 建议 architecture.md §0.1 保持不变，只做 R3 原则内的部分。如果要做"隐藏已订阅博客"或"按订阅推荐博客"，先修订 §0.1 和 accounts.md §0，写明只用读者自己的订阅列表、不收集行为。基于点击和阅读的个性化不建议做：它和"不存数据"这个立身之本冲突，以现在的读者量也学不出什么。

## 5. 待定

- 只给摘要的判断阈值、R1 重评的范围、阅读时长显示。
- R2 的近两天出色和收起规则。
- 收录博客之间的互相引用能不能做信号：先量有多少；它会随时间变化，要和固定排序键一起考虑。
