# Explore 管理后台设计

本文档定义 Explore 管理后台（Admin Dashboard）的产品定位、功能模块、技术架构、API 映射及交互规范。

> 2026-09-25 更新：鉴权已改为本站管理员账号登录，本文关于 Bearer Token 和 `EXPLORE_ADMIN_TOKENS` 的描述已不适用；当前实现见 [admin-operations.md](admin-operations.md)。

---

## 1. 产品定位与原则

管理后台是 Explore 维护者用于日常运营、审核新博客提交、监控博客抓取健康状态、处理作者退出申请与管理黑名单的专用控制台。

### 核心原则

1. **信息密度优先，杜绝花里胡哨**：
   - 管理后台仅供少数维护者使用，无需面向大众的宣传包装，重点是**高信息密度、快速键盘流操作与清晰的状态反馈**。
2. **严格隔离读者侧规则**：
   - 读者侧坚持“零 Cookie、不追踪、严格 CSP、本地无状态”原则；管理后台为受控私有区域，采用维护者 Token 认证，两者网络与会话状态完全隔离。
3. **操作严谨可追溯**：
   - 所有变更操作（审批通过、驳回、修改元数据、下架封禁）均记录操作者身份（`reviewed_by`）与时间戳；
   - 驳回原因必须清晰录入并在公开进度页向提交者透明展示，避免“无理由拒收”。
4. **安全防御严密**：
   - 严格鉴权：所有管理路由必须通过 Bearer Token 验证，后端比较哈希值使用常数时间算法（`subtle.ConstantTimeCompare`），防范时序攻击；
   - 限制暴露：未配置维护者 Token 时管理路由在服务端完全不注册，杜绝攻击面暴露。

## 2. 核心功能模块与业务场景

管理后台划分为四大核心功能模块：

```
                    ┌──────────────────────────────┐
                    │      Explore 管理控制台       │
                    └──────────────┬───────────────┘
                                   │
         ┌─────────────────┬───────┴─────────┬─────────────────┐
         ▼                 ▼                 ▼                 ▼
 ┌───────────────┐ ┌───────────────┐ ┌───────────────┐ ┌───────────────┐
 │ 1. 审核工作台 │ │ 2. 博客治理   │ │ 3. 排除名单   │ │ 4. 诊断与探测 │
 │ 待审队列      │ │ 收录博客列表  │ │ 退出申请名单  │ │ 任意 URL 检测 │
 │ 一键通过/驳回 │ │ 健康度与抓取  │ │ 违规封禁名单  │ │ 报告格式分析  │
 │ 元数据微调    │ │ 立即抓取/下架 │ │ 解除排除      │ │ 抓取测试      │
 └───────────────┘ └───────────────┘ └───────────────┘ └───────────────┘
```

### 2.1 模块一：提交审核工作台（Submissions Queue）

收录审核是维护者最频繁的日常操作。

1. **审核列表（Queue）**：
   - 默认展示状态为 `pending` 的待审提交，按提交时间升序排列（最先提交的排在最前）；
   - 支持按状态切换 tab：`待审核`、`已通过`、`已驳回`；
   - 列表项高信息密度展示：
     - 博客域名（Host）、提交地址（SiteURL）、订阅源（FeedURL）；
     - 博客名称、描述；
     - 探测方式（autodiscovery / direct / candidate 等）；
     - 检测诊断结果：有效文章数、最新文章标题与日期、是否存在警告项（如部分外链等）；
     - 提交者填写的备注说明（Note）。
2. **审核操作**：
   - **一键通过（Approve）**：
     - 允许维护者在确认入库前微调核心元数据：
       - `name`：修改博客名称；
       - `description`：调整博客简介；
       - `feed_url`：确认或更正订阅源地址；
       - `language`：指定主语言（如 `zh-CN`, `en` 等）；
       - `extra_domains`：配置允许的外链/图片域名（如 CDN 或图床域名）；
       - `show_excerpt`：是否在时间流中展示文章摘要。
     - 确认后调用 `POST /api/v1/admin/submissions/{id}/approve`，后端自动完成事务入库，并在后台将该博客立即排入抓取队列。
   - **驳回（Reject）**：
     - 点击驳回时弹出快捷对话框，必须填写 `review_note`（审核说明）；
     - 预置常用驳回模板（如：“非个人原创独立博客”、“缺少 RSS/Atom 订阅源”、“长期未更新停更”、“内容涉及商业营销推广”等）；
     - 确认后调用 `POST /api/v1/admin/submissions/{id}/reject`，提交者在 `/submissions/:id` 进度页可即时看到驳回原因。

### 2.2 模块二：收录博客治理（Blogs Management）

用于维护已收录博客的生命周期与抓取健康状态。

1. **博客检索与健康筛选**：
   - 支持按域名（Host）或博客名称关键字快速搜索；
   - 快速状态筛选：
     - `全部博客`；
     - `异常告警（Unhealthy）`：过滤出连续失败多次、抓取超期或失联（`gone_since`）的博客；
     - `暂停中（Paused）`：人工暂停的博客；
     - `正常运行（Active）`。
2. **博客详情与诊断指标**：
   - **调度与健康指标**：
     - 抓取调度周期（`fetch_interval_seconds`，通常为 1~24 小时动态自适应）；
     - 下次调度时间（`next_fetch_at`）；
     - 上次抓取时间（`last_fetched_at`）与上次成功时间（`last_succeeded_at`）；
     - 连续失败次数（`consecutive_failures`）；
     - 最近一次错误详情（`last_error`，如 DNS 失败、HTTP 502、解析超时等）；
     - 失联时间戳（`gone_since`，连续失败超过阈值后标记为失联，不在前端公开展示）。
3. **运维与治理操作**：
   - **立即抓取（Fetch Now）**：一键使该博客进入立即抓取队列（调用 `POST /api/v1/admin/blogs/{host}/fetch`），无需等待轮询间隔；
   - **抓取队列**：独立页面展示 worker 在线状态、待执行及中断任务、最近错误；每次 worker 领取任务后保存执行记录，可按博客查看最近 20 次结果。`202 Accepted` 仅表示调度时间已更新，实际执行状态以队列页面为准；
   - **编辑元信息**：调用 `PATCH /api/v1/admin/blogs/{host}`，更新博客名称、描述、语言、Feed 地址、默认标签（最多 3 个标签）及额外域名；
   - **暂停 / 恢复抓取**：针对故障站点或临时维护站点，将其状态置为 `paused`，填写 `status_note`，恢复时置为 `active`；
   - **下架移除与排除**：
     - 移除原因类型：
       - `opt_out`：博主申请退出收录（下架并写入排除名单）；
       - `blocked`：违规屏蔽（下架并永久加入黑名单）；
     - 执行后级联清理该博客的所有文章与缩略图，释放存储空间。

### 2.3 模块三：排除名单管理（Excluded Hosts）

1. **排除名单查看**：
   - 调用 `GET /api/v1/admin/excluded-hosts`，列出所有已退出与被屏蔽的域名；
   - 显示原因分类（`opt_out` / `blocked`）、备注说明与加入时间。
2. **解除排除（Delete Exclusion）**：
   - 调用 `DELETE /api/v1/admin/excluded-hosts/{host}`；
   - 当博主重新申请加入、或原封禁理由消除时，解除排除，恢复其重新提交收录的资格。

### 2.4 模块四：在线检查与测试工具（Inspect Tool）

1. 维护者输入任意博客网址或 Feed 网址，调用 `POST /api/v1/admin/check`；
2. 服务端实时运行完整的探测流水线，返回原始的 `check_report`：
   - 包含 HTTP 状态码、ETag/Last-Modified 支持情况、发现方式；
   - 生成器识别（Hugo/Hexo/WordPress 等）；
   - 文章统计（总数、有效数、日期置信度、最新更新时间）；
   - 诊断问题清单与严重级别（Error/Warning/Info）。
3. 方便维护者在无需创建提交记录的情况下，快速排查某个博客无法收录的具体原因。

## 3. 技术架构与选型

### 3.1 前端部署形态选型

针对 `frontend.md §11` 提出的两种做法：
- **方案 A**：在当前 Astro 工程的 `web/` 下开辟 `/admin` 路由，采用整页客户端 React 岛承载；
- **方案 B**：独立构建一个 Vite + React 单页应用（SPA）。

**推荐采用方案 A**：
1. **零部署负担**：与当前前端服务一同打包在 `dist/server/` 中，由单一 Node 进程托管，无需额外配置反向代理或单独的部署流水线；
2. **共享组件与设计体系**：直接复用已有的 `@/components/ui/`（shadcn/ui Button、Input、Badge、Dialog、Table 等）以及 Tailwind CSS 变量；
3. **共享 TypeScript 类型**：直接复用 `web/src/lib/types.ts` 与 API Client，数据契约高度一致；
4. **隔离性保障**：在 Astro 模板层拦截 `/admin`，当未登录时仅展示极简的登录输入框，读者侧页面与管理端互不干扰。

### 3.2 认证与鉴权设计（Auth Flow）

```
 [维护者浏览器]                         [Astro 前端服务]                   [Gin 后端 API]
       │                                      │                                  │
       │ 1. 访问 /admin                       │                                  │
       ├─────────────────────────────────────►│                                  │
       │ 2. 检查本地 sessionStorage token     │                                  │
       │    无 Token -> 渲染登录对话框        │                                  │
       │◄─────────────────────────────────────┤                                  │
       │                                      │                                  │
       │ 3. 输入 Token 并确认                 │                                  │
       │    存入 sessionStorage               │                                  │
       │ 4. 发起 API 请求                     │                                  │
       │    (Header: Authorization Bearer)    │                                  │
       ├─────────────────────────────────────►│ (同源转发 /api/v1/admin/*)       │
       │                                      ├─────────────────────────────────►│
       │                                      │                                  │ 5. 校验 SHA-256 Token
       │                                      │                                  │    匹配成功 -> 200 OK
       │                                      │◄─────────────────────────────────┤
       │ 6. 渲染管理看板与数据列表            │                                  │
       │◄─────────────────────────────────────┤                                  │
```

1. **凭证来源**：
   - 后端通过环境变量 `EXPLORE_ADMIN_TOKENS` 配置维护者列表，格式为 `name:sha256_hash,...`；
   - 维护者持有原始 Token 字符串（例如 32 位随机字符）。
2. **客户端凭证管理**：
   - 维护者首次进入 `/admin` 时输入 Token；
   - 客户端将其缓存在浏览器的 `sessionStorage`（或可选记住在 `localStorage`）；
   - 浏览器发出的所有管理请求通过前端同源路由 `/api/v1/admin/*` 代理，附带 `Authorization: Bearer <token>` 请求头；
   - 若接口返回 `401 Unauthorized`，客户端自动清除本地存储并重新弹出登录认证框。

## 4. API 契约与交互映射

管理后台完整对应后端已实现的 API 接口：

| 功能模块 | HTTP 方法 | API 路径 | 请求参数 / Body | 预期响应 |
|---|---|---|---|---|
| **待审列表** | `GET` | `/api/v1/admin/submissions` | `?status=pending` (或 `approved`/`rejected`) | `200 OK` + 提交数组 |
| **审批通过** | `POST` | `/api/v1/admin/submissions/{id}/approve` | `{ name?, description?, language?, feed_url?, extra_domains?, show_excerpt? }` | `201 Created` + 博客对象 |
| **审核驳回** | `POST` | `/api/v1/admin/submissions/{id}/reject` | `{ review_note: "原因说明" }` | `204 No Content` |
| **博客列表** | `GET` | `/api/v1/admin/blogs` | `?health=unhealthy` (可选) | `200 OK` + 博客数组 |
| **直接添加** | `POST` | `/api/v1/admin/blogs` | `{ site_url, feed_url, name, language, extra_domains, show_excerpt }` | `201 Created` |
| **更新博客** | `PATCH` | `/api/v1/admin/blogs/{host}` | `{ name?, description?, status?, status_note?, default_tags? ... }` | `200 OK` |
| **移除博客** | `DELETE` | `/api/v1/admin/blogs/{host}` | `?exclude=opt_out` (或 `blocked`) | `204 No Content` |
| **即时抓取** | `POST` | `/api/v1/admin/blogs/{host}/fetch` | 无 | `202 Accepted` |
| **排除名单** | `GET` | `/api/v1/admin/excluded-hosts` | 无 | `200 OK` + 排除域名数组 |
| **移除排除** | `DELETE` | `/api/v1/admin/excluded-hosts/{host}` | 无 | `204 No Content` |
| **在线探测** | `POST` | `/api/v1/admin/check` | `{ url: "https://..." }` | `200 OK` + `CheckReport` |

### 5.2 视觉与设计语言

- **主题色调**：遵循 Explore 既有的 `zinc/neutral` 调色板与圆角风格（`border`, `bg-card`, `rounded-lg`），原生支持深色模式与浅色模式跟随；
- **状态徽章（Badges）**：
  - `pending`：黄色/琥珀色（`bg-amber-500/10 text-amber-600`）；
  - `approved` / `active`：绿色（`bg-emerald-500/10 text-emerald-600`）；
  - `rejected` / `unhealthy`：红色（`bg-red-500/10 text-destructive`）；
  - `paused`：灰色（`bg-muted text-muted-foreground`）。
- **信息弹窗（Modals & Drawers）**：
  - 通过审批弹窗支持快速确认与字段编辑；
  - 驳回弹窗提供快捷理由 Chips 标签，点击即填入常用说明，极大提升审批效率。

## 6. 里程碑与实施路线

- **Phase 1（MVP 核心闭环）**：
  1. `/admin` 入口与 Bearer Token 登录/登出弹窗；
  2. 审核工作台：待审队列展示、一键通过（可修改字段）、一键驳回（必填理由）；
  3. 前端同源代理 `/api/v1/admin/*`。
- **Phase 2（运维与监控）**：
  1. 收录博客列表检索、分页与健康状态告警；
  2. 博客即时抓取触发（Fetch Now）与暂停/恢复；
  3. 编辑已有博客的默认标签和基本信息。
- **Phase 3（治理与工具）**：
  1. 排除名单（黑名单/退出申请）管理与解除；
  2. 在线 URL 诊断检测工具。
