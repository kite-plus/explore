## Context：Explore 要解决什么

独立博客的处境：

- **写的人很多，读者找不到。** 好文章散落在成千上万个独立域名上，没有一个地方能看到"大家最近写了什么"。
- **现有的聚合方式大多要求把内容交出去。** 在内容平台发文，内容就留在平台上；转载型聚合站抓取全文，读者不再回到作者的网站。
- **RSS 阅读器只解决订阅，不解决发现。** 前提是你已经知道要订阅谁。

Explore 的目标结果：

> 读者在一个地方看到独立博客最近写了什么；点进去，读的永远是作者自己的网站。

Explore 是 Kite Plus 负责"发现"的部分，但**它不是 Kite 的附属品**。它面向所有博客系统，首批接入 WordPress、Halo、Hugo、Hexo 这些主流系统；Kite 还在开发中，搭好之后以同样的方式接入，不走特殊通道。

## 0. 两个核心判断

### 0.1 只存"有哪些博客"和"谁订阅了什么"，不存"博客写了什么"

"不做数据存储"是 Explore 的立身之本，但需要精确定义，否则会滑向两个极端：要么每次访问都实时去抓所有博客，页面慢，还把源站打垮；要么数据库越积越多，最后变成转载站。

精确的定义：

> **Explore 保存的真相源数据只有两样：博客清单，以及读者自己交给我们的最少账号数据（登录身份和订阅列表）。文章只是源站订阅源和站点地图的一份可丢弃的缓存：标题、链接、发布时间、一句短摘要、缩略图地址，以及 Explore 给它打的标签。正文和图片文件不持久保存，读者的浏览和点击从不记录。**

| 数据 | 处理方式 | 位置 | 丢了会怎样 |
|---|---|---|---|
| 博客清单（收录了谁、审核状态） | **保存**，真相源数据 | PostgreSQL `blogs` | 需要备份；同时通过 OPML 公开 |
| 读者账号（登录身份、昵称、订阅列表、会话） | **保存**；读者随时可以删除，删除立即生效 | PostgreSQL `users`、`subscriptions`、`sessions`（[accounts.md §6](accounts.md#6-数据模型)） | 需要备份 |
| 文章元数据（标题、链接、发布时间、短摘要、缩略图地址） | 只缓存 | PostgreSQL `entries`、`sitemap_urls` | 下一轮抓取、读站点地图和读文章页后完全恢复 |
| 文章标签（Explore 用模型打的） | 只缓存，跟着文章走 | PostgreSQL `entries` | 下一轮重新打，个别结果可能不同 |
| 抓取状态（ETag、Last-Modified、失败计数） | 只缓存 | PostgreSQL `blogs` 的抓取字段 | 多一轮完整下载，不影响正确性 |
| 文章正文、图片文件 | **不持久保存**；缩略图字节仅在内存中短时缓存 | —— | 原文和图片仍在作者的站点 |
| 读者行为（浏览、点击、阅读记录、IP 明细） | **从不收集** | —— | —— |

读者账号是 2026-09-23 加上的（§13）：读者登录后可以订阅博客，在订阅流里追更。它只存完成这件事必需的数据；不登录照样能看全部公开内容，匿名访问零 Cookie。细节见 [accounts.md](accounts.md)。

这和 Kite 对自己索引的定位是同一个思路：Kite 在 `.kite/` 下的索引只是缓存，删掉重建，数据完全一样。

**可验证**：清空 `entries` 和 `sitemap_urls`，订阅源抓取、读站点地图和读文章页（§6.5、[worker.md §13](worker.md#13-站点地图)）都跑完之后，所有页面与清空前一致（这期间真正从源站消失的文章除外）。这条写成了自动化测试，在 CI 里跑（[data-model.md §6](data-model.md#6-schema-守护)）。`entries` 表在 schema 上就没有正文字段——不是"约定不存"，而是"存不进去"。

**推论：展示规则只能依赖订阅源本身和当前时间。** 规则一旦依赖 Explore 自己记下的历史（比如首次发现时间、点击量），清空重建后结果就会变，缓存也就不再可丢弃。所以：

- 文章离开源站，也就是订阅源和站点地图里都没有了，就离开 Explore。作者删文、改标题，下一轮抓取后自动同步，不需要单独的下架流程。订阅源只带最近的文章，更早的由站点地图补上，所以文章不会因为挤出订阅源就消失。
- 没有发布时间的文章不进首页时间流，只在该博客的页面列出；发布时间在未来的文章，到时间再出现。
- 每个博客保留订阅源里的文章，加上站点地图列出的历史文章，站点地图部分最多 1,000 篇（`policy.SitemapMaxPosts`）。Explore 只索引源站此刻公开的文章，不做归档，缓存总量仍有上限（博客数 × 上限）。
- 不做热度排序和个性化推荐，这些数据我们本来也不收集。
- 文章标签由模型根据文章内容打出来，不依赖 Explore 记下的历史。但模型的结果不是逐字确定的，清空重打后个别文章的标签可能不同。这是"清空前后一致"唯一的例外，只影响按标签筛选（[accounts.md §5.2](accounts.md#52-怎么打)）。

**为什么不每次访问都实时抓取**：一次页面访问要扇出到几百个站点，延迟取决于最慢的那个；读者越多，源站压力越大，而独立博客往往跑在便宜的主机上。缓存加礼貌轮询，让源站承受的请求量只跟博客数量有关，跟读者数量无关。

### 0.2 只认开放标准，不给任何系统开后门

Explore 只通过开放的订阅格式采集：**RSS 2.0、Atom 1.0（RFC 4287）、JSON Feed 1.1**，用 HTML 里的 `<link rel="alternate">` 自动发现订阅地址。不解析网页正文，不对接任何博客系统的私有 API。订阅源缺缩略图或摘要被截断时，只读文章页 `<head>` 里的 Open Graph 和 meta 标签补上（§6.5）。订阅源只带最近的文章，更早的从站点地图（sitemaps.org 协议）找到，标题、发布时间、封面和摘要同样取自文章页 `<head>` 里的 Open Graph、meta 和 JSON-LD（[worker.md §13](worker.md#13-站点地图)）。它们都是开放标准，正文仍然不解析。

**为什么**：

- 主流博客系统都原生或通过官方插件输出这些格式（见 [§5](#5-接入的博客系统)）。WordPress、Halo、Hugo 的作者不需要为 Explore 改任何东西，Hexo 只需装上官方的订阅插件。
- 每对接一个私有 API，就多一份跟着上游版本失效的维护负担；订阅格式十几年没有变过。
- Kite 搭好后也走同一条路。它"无缝接入"的方式是**把订阅源做成标准的好样本**，而不是让 Explore 为它写专属代码。Kite 站点在排序和展示上没有任何特权。

**推论**：任何系统想要的增强能力（发布即出现、所有权验证），都必须表达成**任何博客都能实现的开放协议**，例如 WebSub、ping、网页 meta 标签，而不是某个系统专属的接口。系统之间的差异只允许出现在两处：检查时尝试的默认订阅地址，以及给作者的修复提示。

## 1. 产品定位

**Explore 是一个只做索引、不做托管的独立博客聚合站**：汇集博客公开的订阅源，按时间流展示标题和摘要，读者点击后回到作者自己的网站阅读。

- **对读者**：打开就能看到独立博客最近写了什么，不用注册，不被追踪；想追更，就登录订阅喜欢的博客。
- **对作者**：多一个被读到的入口，不用交出内容，也不用换博客系统。从 Explore 过去的读者，会出现在作者自己的访问统计里。
- **对 Kite Plus**：补上"创作 → 发布 → 发现"的最后一环。

**不是什么**（防止定位漂移）：

- 不是内容平台或社区：没有发帖、评论、点赞、关注。
- 不是转载站：不保存、不展示正文，阅读永远发生在源站。
- 不是 RSS 阅读器：不管理个人订阅。想长期追读，可以导出 OPML 放进自己的阅读器。
- 不是搜索引擎或全网爬虫：只收录经过审核加入的博客。
- 不是 Kite 的附属功能：任何有标准订阅源的博客都能加入。

## 2. 目标与非目标

### 2.1 V1 目标

1. **作者**：WordPress、Halo、Hugo 的默认订阅源，以及装了官方订阅插件的 Hexo，都开箱即用；提交博客地址后立即得到检查结果，审核通过后新文章在一个轮询周期内出现（默认 ≤ 60 分钟 `[待定]`）；申请退出后立即从 Explore 消失。
2. **读者**：打开 explore.kite.plus 看到按发布时间倒序的最新文章（标题、博客名、发布时间、短摘要），点击直达原文；页面能被搜索引擎正常收录（[§8](#8-前端与-seo)）。登录（邮箱验证码或 GitHub）后可以订阅博客，在推荐流和订阅流之间切换，两条流都能按标签筛选（[accounts.md](accounts.md)）。
3. **系统**：数据库里没有正文，也没有读者的浏览和点击记录；单个 worker 承载 1,000 个博客。

### 2.2 明确不做

| 不做 | 原因 |
|---|---|
| 保存或展示正文、保存图片文件 | §0.1。列表只展示源站订阅源提供的缩略图，点击仍回到原文 |
| 评论、点赞、基于个人行为的推荐 | 需要记录读者行为，违背 §0.1。账号和订阅要做，见 [accounts.md](accounts.md) |
| 点击追踪、第三方统计、广告 | 同上，也是对读者的承诺 |
| 全网爬取、自动发现博客 | 只收录经过审核加入的博客 |
| 解析网页 HTML 抓文章 | §0.2，只认订阅格式 |
| 为某个博客系统写专属对接 | §0.2 |
| 单篇文章的落地页 | 不和作者争搜索排名（§8） |
| 历史归档 | 每个博客只保留最新 N 篇 |

## 3. 用户与场景

设计决策冲突时，按此优先级裁决。

| 优先级 | 用户 | 诉求 | 对设计的约束 |
|---|---|---|---|
| **P0** | 博客作者 | 被更多人读到，内容留在自己手里 | 加入和退出都简单；链接直达原文；可以关掉摘要 |
| **P0** | 读者 | 发现值得读的博客和新文章，追更喜欢的博客 | 不登录也能看全部内容；页面快；不被追踪；登录只为订阅 |
| P1 | 维护者 | 审核收录、处理举报、保持质量 | 提交时自动检查；下架快 |
| P2 | Kite 用户（Kite 搭好后） | 发布后自动出现在 Explore | 通过开放协议实现，不开后门 |

- **S1 作者加入**：提交博客地址 → 系统自动找到订阅源并检查，当场列出问题（例如"文章链接指向 example.com，请检查站点地址配置"）→ 维护者审核通过 → 一个轮询周期内，新文章出现在首页。
- **S2 读者浏览**：打开首页按时间浏览近期文章 → 点击标题，在作者的博客上阅读 → 点博客名，看这位作者最近写了什么 → 登录后订阅这个博客，以后在订阅流里看它的新文章；也可以用作者自己的订阅源订阅。
- **S3 作者退出**：申请移除后，博客和它的全部文章立即从 Explore 删除。站点对抓取器返回 `410 Gone`，或在 robots.txt 里禁止 `KiteExplore`，也视为退出。
- **S4 维护者处理问题**：某个博客的订阅源被劫持、开始投放广告链接 → 链接不在该博客的域名内，被自动丢弃（§6.3）→ 维护者暂停或移除这个博客。

## 4. 收录

### 4.1 收录方式 `[设计中]`

1. 作者提交博客地址，订阅地址可选。E2 前端上线前，由维护者通过管理接口代为录入。
2. 系统自动运行检查（§4.3），当场返回结果；不通过时附上具体原因和修复建议。
3. 维护者审核通过后开始抓取。
4. 维护者是否可以直接收录推荐的博客，见 [§13](#13-待确认的问题)。

退出永远比加入容易：作者申请移除即生效；站点返回 `410 Gone`，或在 robots.txt 里禁止 `KiteExplore`，也视为退出。

全部收录的博客通过 `/blogs.opml` 公开。任何人都可以把整份清单导入自己的阅读器带走——Explore 不是围墙花园。

### 4.2 收录标准 `[待定]`

- 个人或独立博客；
- 有可用的 RSS、Atom 或 JSON Feed；
- 近 12 个月内有更新；
- 不收商业营销、内容农场、批量生成或搬运的内容。

V1 是否只收独立域名（包括 GitHub Pages 这类子域名），还是也收内容平台上的个人主页，见 §13。

### 4.3 自动检查

检查逻辑是一个独立的包，四处复用：命令行 `explore check <url>`（作者自查、维护者排错）、提交接口（当场返回结果）、worker（持续监测博客健康）、E0 实测（批量统计真实订阅源的质量）。

1. **找到订阅源**：先看首页的 `<link rel="alternate">`；找不到时按各系统的默认地址依次尝试（§5.1，顺序见 [worker.md §6.1](worker.md#61-找到订阅源)）。不能只靠自动发现：本地 Halo 2.26.1 的默认主题 theme-earth 首页就没有输出这个标签 `[EV]`。
2. **能访问、能解析**：状态码、格式、字符编码、体积上限。
3. **内容可用**：有发布时间；链接是绝对地址，且落在博客自己的域名内；近 12 个月有更新。
4. **记录**：从订阅源的 `<generator>` 识别博客系统，报告是否支持条件请求。

## 5. 接入的博客系统

按 §0.2，Explore 不为任何系统写专属对接。下面这些差异只影响两件事：检查时按什么顺序尝试默认订阅地址，以及检查不通过时给作者什么提示。

各系统的默认行为按 2026-09-23 的当前版本源码核对；标 `[EV]` 的另外做过本地实测。

### 5.1 首批：WordPress、Halo、Hugo、Hexo

| | WordPress 7.1 | Halo 2.26 | Hugo 0.166 | Hexo 8.1 |
|---|---|---|---|---|
| 订阅源来源 | 内置 | 官方订阅插件，默认预装并启用 | 内置 | 需要安装 `hexo-generator-feed`，`hexo init` 的初始站点不带 |
| 默认地址 | `/feed/` | `/rss.xml` | `/index.xml` | `/atom.xml` |
| 格式 | RSS 2.0（另有 Atom） | RSS 2.0 | RSS 2.0 | Atom（可另开 RSS 2.0） |
| 默认条数 | 10 | 20 | **全部** `[EV]` | 20 |
| 内容 | 全文 | 摘要 | 摘要 `[EV]` | 全文加摘要 |
| 文章身份 | `guid`：`?p=ID` 形式的地址 | `guid`：相对路径 `[EV]` | `guid`：文章地址 | Atom `id`：文章地址 |
| 自动发现 | 区块主题自带；经典主题要主题声明支持 | 没有 `[EV]` | 取决于主题 | 插件默认注入 |
| 条件请求 | 支持（`ETag`、`Last-Modified`） | 不支持 `[EV]` | 取决于托管 | 取决于托管 |

对 Explore 的要求（都已落到 §4.3 的检查或 §6 的规则里）：

**WordPress**

- 默认输出全文（`content:encoded`）。摘要按 §6.5 从 `description` 截取，全文不入库。
- `guid` 是文章创建时写入的地址，比如 `http://旧域名/?p=123`，换域名或升级 https 后仍保留旧值：只当身份键，永远不去访问它（§6.2）。
- 订阅源只有最新 10 篇。两次轮询之间发文超过 10 篇会漏掉中间的，对个人博客可以接受。
- 支持条件请求，是四个系统里对抓取最友好的。

**Halo**

- 抓取请求的 `Accept` 头必须包含 `application/rss+xml`、`text/xml` 或 `*/*`：Halo 按 `Accept` 匹配订阅路由，只写 `application/atom+xml` 或 `application/xml` 时匹配不到。
- 优先用 `/rss.xml`。文章更新时插件会清掉 `/rss.xml` 的缓存，却不清 `/feed.xml`，后者最长可能滞后 60 分钟。
- 插件自带 60 分钟的内存缓存，轮询得比这更勤没有意义。不支持条件请求，就靠响应体哈希判断有没有变化（§6.1）。
- `pubDate` 里的日期可能是一位数，比如 `Thu, 3 Sep 2026 01:02:03 GMT`，解析必须宽松。
- 每条摘要开头都有一张 1×1 的统计图片 `[EV]`，按 §6.5 去掉。
- 官方 Docker 部署示例把外部访问地址设成 `http://localhost:8090/`。照抄却没改的站点，订阅源里的链接全指向 localhost，会被 §6.3 的域名规则拦下，检查时提示作者修改 `halo.external-url`。

**Hugo**

- 默认把**全部**页面写进订阅源 `[EV]`，文章多的站点订阅源能有好几 MB。5 MiB 的体积上限和"每个博客只保留最新 N 篇"主要为它准备。
- 首页订阅源 `/index.xml` 会混进 About 这类独立页面 `[EV]`。检查时如果 `/posts/index.xml` 存在，建议改用它。
- 条目先按权重、再按日期排序。Explore 自己按发布时间排序，不依赖订阅源里的顺序。
- 没写日期的文章输出 `0001-01-01` `[EV]`，按 §6.4 视为没有发布时间。
- `hugo new site` 默认的 `baseURL` 是 `https://example.org/` `[EV]`。没改的站点链接全指向 example.org，会被 §6.3 拦下并提示。

**Hexo**

- 订阅源来自插件。如果页面声明了 `/atom.xml` 却返回 404（默认主题 landscape 在没装插件时就是这样），检查时提示作者安装 `hexo-generator-feed`。
- 初始配置 `_config.yml` 里的 `url` 是 `http://example.com`。没改的站点链接全指向 example.com，会被 §6.3 拦下并提示。
- 插件 4.0.0 输出 RSS 2.0 时不带 `guid`（上游已知问题），按 §6.2 退回用链接作身份。
- 没写 `date` 的文章用文件创建时间作发布时间，而 CI 每次检出都会重置这个时间，于是这类文章每次部署都像刚发布。按 §6.4 的"日期不可信"规则处理。
- 默认输出全文；摘要取 `description`、`excerpt`，都没有时取 HTML 的前 140 个字符，可能截断标签。Explore 统一从纯文本重新截取摘要。

### 5.2 下一批

Typecho、Jekyll、Ghost 同样开箱输出标准订阅源。E0 顺带实测，达标就提前列入首批。

| | 默认地址 | 格式 | 条数 | 需要注意 |
|---|---|---|---|---|
| Typecho 1.3 | `/index.php/feed/`（开启伪静态后为 `/feed/`） | RSS 2.0 | 10 | 不支持条件请求；订阅地址不规范时会 301；开启伪静态会改掉全部链接和 `guid` |
| Jekyll（jekyll-feed） | `/feed.xml` | Atom | 10 | `jekyll new` 生成的 `url` 为空，链接是相对路径 |
| Ghost 6 | `/rss/` | RSS 2.0 | 15 | 付费文章在订阅源里被截断或为空；私有模式下没有订阅源 |

### 5.3 Kite（开发中）

Kite 还在开发，接入排在主流系统之后（E4）。按 §0.2，Explore 不为它写专属代码，Kite 要做的是成为一个标准的好样本。按当前代码实测 `[EV]`：

| 项 | 现状 | 影响 | 需要 Kite 做的 |
|---|---|---|---|
| `kite build` 静态站 | 输出 RSS 2.0 `/rss.xml`，页面带 `<link rel="alternate">` | 已经可以接入 | —— |
| `kite serve` / `kite run` 部署 | 页面声明了 `/rss.xml`，请求却返回 404，`/sitemap.xml` 也一样 | 用服务器运行的 Kite 站点无法接入 | 服务端运行时也提供订阅源 |
| `<guid>` | 稳定的 ULID，但没有标 `isPermaLink="false"` | Explore 只当身份键，不受影响；RSS 2.0 规定缺省即视为链接，其他阅读器可能误用 | 加上 `isPermaLink="false"` |
| 未配置 `baseURL` | 条目链接是相对路径 | Explore 会按订阅地址解析；其他阅读器可能出错 | 构建时给出警告 |

### 5.4 发布即出现 `[待定]`

轮询是底线。想让新文章更快出现，靠开放协议，并且对所有系统一视同仁：

- **ping**：Explore 提供一个 ping 地址，只触发对已收录博客的一次限速抓取，不能新增博客，也不能写入任何内容。WordPress 自带的"更新服务"（设置 → 撰写）会在发布时向列表里的地址发送 ping，兼容它之后，作者把地址加进列表即可（E3 验证）；Kite 可以在 `kite publish` 之后调用。
- **WebSub**：W3C 标准，但四个系统目前都不能开箱即用：WordPress 要装插件，Hexo 订阅插件的 `hub` 选项只输出声明、不会通知。E3 再评估。

## 6. 抓取与展示规则

### 6.1 礼貌抓取 `[设计中]`

独立博客常跑在便宜的主机上，抓取器必须是个好邻居。实现细节见 [worker.md](worker.md)。

| 项 | 默认 |
|---|---|
| User-Agent | `KiteExplore/0.1 (+https://explore.kite.plus/bot)`；中英对照的说明页写清用途、频率和退出方式 |
| Accept | 列出 RSS、Atom、JSON Feed 的媒体类型，再加 `*/*`。Halo 按 `Accept` 匹配订阅路由（§5.1） |
| 条件请求 | 只带一个校验值：有 `Last-Modified` 就发 `If-Modified-Since`，否则发 `If-None-Match`（E0 实测，见 [worker.md §3.6](worker.md#36-变化检测)）；服务器不支持时比较响应体哈希，没变化就跳过解析 |
| 轮询间隔 | 默认 60 分钟；连续没有更新时逐步放宽到 6 小时，有更新后恢复 |
| 限流与失败 | 尊重 `429`、`503` 的 `Retry-After`；连续失败指数退避；7 天没有成功抓取的博客暂不展示，恢复后自动回来 |
| 单次限制 | 超时 30 秒，响应体 ≤ 5 MiB，最多 5 次重定向；同一主机同一时间只有一个请求。超时原是 15 秒，但从海外下载一个 1.6 MB 的订阅源实测要 13 秒 `[EV]` |
| 退出信号 | `410 Gone`，或 robots.txt（按 RFC 9309）里针对 `KiteExplore` 的规则组禁止了订阅地址：立即停止展示，持续 7 天后移除并记入排除名单。只写给所有爬虫的 `*` 组不算退出：照样不抓，但按普通失败处理（[worker.md §3.4](worker.md#34-结果分类)） |
| 安全 | 拒绝连接内网、回环、链路本地地址，重定向之后同样检查，防止 SSRF；重定向的目标也要过 robots.txt |
| 原文链接检测 | 后台每分钟最多检查 8 篇，每个博客每轮最多 1 篇；读者可立即检测尚未检查的文章，每个客户端地址每小时最多请求 10 次，全站最多同时运行 4 次。两种入口共享文章租约；先发 HEAD，不能确认时用只请求首字节的 GET；单次超时 10 秒。成功或 404/410 每 24 小时复查，其他结果 6 小时后重试 |

### 6.2 文章身份

同一个博客内，用 RSS 的 `guid` 或 Atom 的 `id` 识别文章，没有时用规范化后的链接。身份键只用来去重，不当作链接使用：本地 Halo 2.26.1 的 `guid` 是 `/archives/hello-halo` 这样的相对路径 `[EV]`，Kite 的是 ULID。

### 6.3 链接：跳回源站的保证

- 只接受 `http`、`https`，拒绝 `javascript:` 之类的地址；相对链接按订阅源地址解析成绝对地址。
- **文章链接必须落在博客自己的域名内**，否则丢弃。"自己的域名"指与站点属于同一个可注册域名（例如 `www.example.com` 与 `example.com`；而 `alice.github.io` 与 `bob.github.io` 不算），或收录时声明的额外域名。这一条同时解决三件事：兑现"点击回到作者网站"的承诺；订阅源被劫持时，无法借 Explore 投放外链；站点地址配错时，检查会直接指出来（见 §5.1 的 Hexo）。
- 链接原样输出：不经过 Explore 的跳转页，不加追踪参数。页面使用 `Referrer-Policy: strict-origin-when-cross-origin`（也是浏览器的默认值），作者在自己的统计里能看到来自 explore.kite.plus 的访问，而 Explore 自己不记录任何点击。
- 文章旁显示最近的链接检测状态：成功时只显示绿色的圆形对号，404/410 显示红色“疑似失效”，未检查、超时或抓取器被拒绝时显示暖色“待检测”或“状态待确认”。“待检测”可点击立即检测，检查期间显示进度并等待结果。检测时间可以在状态提示中查看。源站对抓取器和读者可能返回不同结果，因此仍保留原文链接。

### 6.4 时间

- 按发布时间排序：RSS 的 `pubDate`，Atom 的 `published`，没有时退回 `updated`。这样修改旧文不会把它顶上首页，除非订阅源只提供 `updated`。
- 日期解析兼容常见的不规范写法，比如 Halo 的一位数日期。
- 没有发布时间或是零值日期（如 Hugo 输出的 `0001-01-01`）的文章不进首页时间流。
- 发布时间在未来（容许 1 小时时钟误差）的文章，到时间再出现。
- **日期不可信**：同一个订阅源里，超过 5 篇文章的发布时间精确到分钟都相同，就视为日期不可信（典型是 CI 构建、没写日期的 Hexo 站点、旧文批量导入），这些文章不进首页时间流。E0 实测的依据见 [worker.md §10](worker.md#10-e0-实测)。这条只看当前快照，不需要记住历史，符合 §0.1 的推论。

### 6.5 摘要

- 从 `description`、`summary` 或 `content` 取，抓取时就去掉全部 HTML，截成 ≤ 140 字的纯文本 `[待定]`。原始 HTML 从不入库、从不渲染。E0 实测：订阅源自带的摘要，中文的中位数约 100 字，英文约 260 个字符；140 字会截断三分之一的中文摘要、七成的英文摘要（§13 第 4 问）。
- 摘要为空，或被截成 WordPress 那样的「[…]」时，改用文章页 `<head>` 里的 `og:description`（其次 `description`、`twitter:description`），同样截成 ≤ 140 字。
- 缩略图先取订阅源提供的图片地址，跳过已标明为 1×1 的统计图；订阅源没有时，取文章页 `<head>` 里的 `og:image`（其次 `twitter:image`）。同一博客多篇文章共用的页面图片和描述是站点默认值，不是这篇的封面和摘要，不展示。页面里针对所有抓取器或 `KiteExplore` 的 robots meta 会被遵守：`noindex` 两样都不取，`nosnippet` 不取摘要，`noimageindex` 不取图片。读页的规则见 [worker.md §12](worker.md#12-读文章页)。读者请求本站的图片接口；服务端检查 robots.txt、目标地址、类型、尺寸和体积后代读者获取，字节只在内存中短时缓存，图片文件不入库。图片失败时页面去掉缩略图，文章仍以文字显示。
- 不直接渲染订阅源 HTML：本地 Halo 2.26.1 的订阅插件会在摘要里嵌一张 1×1 的统计图片 `[EV]`，直接渲染会让读者只是浏览列表就向源站发出统计请求。
- 作者可以关闭摘要，只展示标题。

### 6.6 首页时间流

- 首页是「最新」：按发布时间倒序，按页往下翻，不限时间范围，缓存里的文章都能翻到。另有「推荐」和「订阅」两条流，见 [accounts.md §3](accounts.md#3-三条信息流)。
- 防刷屏：同一个博客在首页每天最多显示 3 篇 `[待定]`，其余在博客页可见。

## 7. 系统架构

```text
          blogs: WordPress / Halo / Hugo / Hexo / ...
             |                                   ^
             | RSS / Atom / JSON Feed            | reader opens the
             v                                   | original link
   worker: fetch, parse, normalize, tag, check links |
             |                                   |
             v                                   |
   PostgreSQL: blogs, entries, users, ...        |
             |                                   |
             v                                   |
   api: Gin, /api/v1, /feed.xml, /blogs.opml     |
             |                                   |
             v                                   |
   web: Astro, server-side rendered -------------+
```

### 7.1 组成

| 组成 | 职责 |
|---|---|
| worker | 调度抓取；条件请求、限速、退避；解析并规范化；把每个博客的最新快照同步进 `entries`；给新文章打标签（Claude API，[accounts.md §5](accounts.md#5-文章标签)） |
| api | Gin，提供 `/api/v1`，以及 `/feed.xml`、`/blogs.opml`；读者的登录、会话和订阅 |
| web | 前端，Astro 服务端渲染，只在服务端调用公开 API（§8） |
| PostgreSQL | 博客清单、文章缓存、提交记录、读者账号与订阅 |

一个二进制 `explore`，子命令 `serve`（API）、`worker`（抓取）、`check`（检查单个博客）、`migrate`（数据库迁移）。api 和 worker 分开部署，重启互不影响。目录、包的划分和依赖规则见 [project-layout.md](project-layout.md)。

### 7.2 数据模型

| 表 | 性质 |
|---|---|
| `blogs` | 真相源：收录了哪些博客，附带抓取状态 |
| `entries` | 可丢弃的缓存：各博客订阅源此刻的样子。**没有正文字段**，摘要在数据库层面限制在 140 字以内 |
| `submissions` | 收录流程：提交与审核 |
| `excluded_hosts` | 已退出或被屏蔽的主机名，保证退出之后不会被重新收录 |

读者账号、会话和订阅的表见 [accounts.md §6](accounts.md#6-数据模型)；维护者用具有后台权限的账号登录，见 [admin-operations.md](admin-operations.md)。每次抓取成功后，在一个事务里用订阅源的最新快照替换该博客的条目。表结构、同步事务、查询和 schema 守护见 [data-model.md](data-model.md)。

### 7.3 API

Gin 提供 `/api/v1` 下的公开接口（首页时间流、博客目录、博客页、提交与进度查询）和管理接口（审核、暂停、移除、排除名单），以及 `/feed.xml`、`/blogs.opml`。

分页用游标 `(published_at, id)`，不用 offset：新文章不断插入时，offset 分页会让读者翻页时看到重复或漏掉文章。完整设计见 [api.md](api.md)。

### 7.4 技术选型

| 方面 | 选择 | 状态 |
|---|---|---|
| 后端 | Go + Gin | 已定 |
| 数据库 | PostgreSQL 16+ | 已定 |
| 前端 | 前后端分离；Astro 服务端渲染，Tailwind CSS v4 + shadcn/ui，交互组件用 React（[frontend.md](frontend.md)） | 已定 |
| 数据访问 | `pgx`，SQL 手写在 `internal/store` 里：查询里有窗口函数、`SKIP LOCKED` 和批量 upsert，直接写 SQL 比 ORM 清楚，每条查询都有集成测试 | `[设计中]` |
| 数据库迁移 | `goose`，SQL 文件嵌入二进制 | `[设计中]` |
| 订阅源解析 | `gofeed`，覆盖 RSS、Atom、JSON Feed | `[设计中]`，E0 用真实订阅源验证 |
| 摘要清理 | `golang.org/x/net/html` 提取纯文本 | `[设计中]` |
| 部署 | Docker Compose：postgres、migrate、serve、worker | `[设计中]` |

版本与其余依赖见 [project-layout.md §5](project-layout.md#5-技术选型与版本)。抓取调度用 `FOR UPDATE SKIP LOCKED` 领取到期的博客，V1 只跑一个 worker，将来加 worker 不需要改表结构，也不需要引入消息队列（[worker.md §2](worker.md#2-调度)）。

## 8. 前端与 SEO

前后端分离，前端用 **Astro** 做服务端渲染，在 E2 开发。页面、组件规则、缓存和 SEO 清单见 [frontend.md](frontend.md)。这里只写不能动摇的约束，它们也反过来约束 API 和数据模型：

- **服务端输出完整 HTML**。前后端分离不等于单页应用：读者页面不能做成纯前端渲染，百度执行 JavaScript 的能力远不如 Google。
- **默认零 JS**：页面默认只有 HTML 和 CSS，只有需要交互的组件才在浏览器里运行（Astro 的"岛"）。
- **中英双语**：中文在根路径，英文在 `/en/`，两种语言的页面用 `hreflang` 互相声明。只翻译界面，博客的标题和摘要永远保持原文（[frontend.md §3](frontend.md#3-多语言)）。
- **可被收录的页面**：首页、博客目录、每个博客的页面，将来加主题页。每页有独立的标题、描述、canonical 和 Open Graph 信息；`sitemap.xml` 列出全部博客页。翻页和筛选后的列表页不收录。
- **不生成单篇文章的落地页**。文章在 Explore 上只以链接的形式出现。有人搜索文章标题时，排在前面的应该是作者的原文，而不是 Explore——这是聚合站和转载站的分界线。
- 指向原文的链接是普通链接，不加 `nofollow`，把搜索引擎也引向作者的网站。
- 匿名读者零 Cookie、零第三方请求（CSP `default-src 'self'`）；登录后只有一个会话 Cookie，个人化的页面不缓存、不收录（[accounts.md §8](accounts.md#8-前端)）。缩略图和博客 favicon 都从本站图片接口加载，不外链图片和字体；favicon 缺失时头像用名称生成。
- 前端只在服务端调用公开 API，不直连数据库。

## 10. 成功指标

Explore 不追踪读者，所以指标只来自系统自身：

- 收录的博客数，以及按博客系统的分布；
- 健康博客占比（最近一次抓取成功）；
- 从发布到出现在 Explore 的中位延迟；
- 每月提交数与审核通过数；
- 作者反馈：来自 explore.kite.plus 的访问出现在作者自己的统计里（由作者自愿分享）。

运行日志只保留聚合计数（请求量、抓取成功率），不记录读者 IP 明细。

## 11. 风险

| 风险 | 表现 | 缓解 |
|---|---|---|
| "不存储"被做歪 | 要么每次访问实时抓取；要么数据库越积越多，成了转载站 | §0.1 的定义；`entries` 没有正文字段；清空恢复测试 |
| 订阅源质量参差 | 乱码、没有日期、相对链接、全文塞进摘要、链接指向错误域名 | E0 实测后定规则；提交时检查拦截 |
| 垃圾与违规内容 | 订阅源被劫持投放外链；违法内容 | 审核收录；链接必须在博客域名内；屏蔽清单；快速下架 |
| 刷屏 | 高频博客霸占首页 | 每个博客每天的展示上限 |
| 冷启动 | 博客太少，首页空 | 首批邀请制，先联系作者本人 |
| 审核成为瓶颈 | 提交堆积 | 自动检查先过滤；将来用所有权验证（例如 meta 标签）让通过检查的作者自助加入 |
| 合规 | 展示第三方内容，要能及时处理举报和下架请求；有了读者账号，还要讲清存了什么、怎么删 | 部署在中国大陆以外，不做 ICP 备案（§13）；作者按关于页的方式申请退出即生效；E3 做举报与下架流程；关于页写明账号数据，设置页可以删除账号 |
| 账号被盗用、验证码被滥发 | 会话被盗；有人借接口给别人狂发验证码 | 只存会话令牌的哈希；Cookie 设 `HttpOnly`、`Secure`、`SameSite`；验证码按邮箱和地址限流（[accounts.md §2](accounts.md#2-账号)） |
| 打标签的费用和质量 | 清空缓存后一次重打上万篇；模型分错类 | 超过阈值改用 Batches 半价；标签只影响筛选，不影响文章是否出现；维护者可以给博客设默认标签；上线前实测准确率和费用 |
| 抓取器被当成攻击 | 被封 IP、被投诉 | 清晰的 User-Agent 和说明页；条件请求；自适应频率；尊重 robots.txt 和 429 |

## 12. 现在必须定的，和现在不做的

**现在必须定**（定错了，后面是重写级代价）：

1. §0.1 的定义：`entries` 没有正文字段；清空恢复测试从第一个 commit 起进 CI。
2. 只认开放订阅格式（§0.2）：代码里永远不出现某个系统专属的分支。
3. 文章身份：`(blog_id, 身份键)`，身份键取 `guid` 或 `id`，没有时用规范化链接。
4. 链接规则：原始链接、只允许 http(s)、必须落在博客域名内、不经跳转页。
5. 展示规则只依赖订阅源和当前时间（§0.1 的推论）。
6. 游标分页，不用 offset。

**现在不做**（判断标准同 Kite：将来做时只需新增代码、不需修改已有接口，就现在不做）：

| 不做 | 现在只需要 | 何时 |
|---|---|---|
| 前端 | 把 SEO 要求落进 API 设计（§8） | E2 |
| 发布即出现（ping、WebSub） | 调度支持"立即抓取某个博客" | E3 |
| 多个 worker | 调度用 `next_fetch_at` + `FOR UPDATE SKIP LOCKED` | 单个 worker 跟不上时 |
| 所有权验证、自助加入 | —— | 审核成为瓶颈时 |
| 维护者账号 | 配置里的访问令牌 | E3 做管理界面时 |
| 搜索 | —— | E5，届时评估 PostgreSQL 全文检索与中文分词扩展 |
| 个性化推荐 | —— | 要记录读者行为，与 §0.1 冲突，默认不做 |
| 非博客内容（播客、相册、文档站） | 数据模型不写死"博客文章" | 有需求时 |

## 13. 待确认的问题

1. **"不做数据存储"**：已确认，按修订后的 §0.1 执行：读者账号只存登录身份和订阅，不记录浏览行为（见下表）。
2. **收录范围**：只收独立域名，还是也收 CSDN、博客园、掘金这类平台上的个人主页？
3. **收录方式**：以作者自荐为主，是否也允许维护者直接收录推荐的博客？
4. **摘要**：默认展示 ≤ 140 字纯文本，作者可以关闭。长度和默认值是否合适？E0 实测：140 字截断三分之一的中文摘要、七成的英文摘要（英文只剩约 25 个词）。一个办法是按显示宽度截断：中文 140 字，英文 280 个字符。
5. **部署地**：已确认，见下表。
6. **首批博客**：E2 上线时的种子名单从哪里来？E0 把[中文独立博客列表](https://github.com/timqian/chinese-independent-blogs)的 1,484 个博客全部检查了一遍，目前有 630 个（42%）能通过，可以作为邀请名单的来源。
